PawSQL SQL Quality Gate 将 SQL Review、风险检测和性能规则嵌入 CI/CD 流程，使 SQL 质量控制从人工发布检查升级为自动化上线门禁。

它可以在 SQL 进入测试或生产环境之前，根据企业策略自动决定：**通过、告警或阻断**。

## 概览

在传统数据库发布流程中，SQL 审核往往发生在上线前的最后阶段：

1. 开发提交 SQL
2. DBA 人工检查
3. 发现问题后退回修改
4. 再次提交
5. 发布

这种方式依赖人工经验，也容易成为持续交付流程中的瓶颈。

SQL Quality Gate 将审核能力自动嵌入 Pipeline：

## 为什么 SQL 质量门禁很重要

代码已经普遍使用：

- Unit Test
- Static Analysis
- Security Scan
- Code Quality Gate

但 SQL 在很多企业中仍然依赖上线前人工审核。

SQL Quality Gate 的目标是把数据库质量控制纳入软件工程体系，让 SQL 和应用代码遵循类似的持续质量机制。

## 核心能力

### 自动化 SQL 审核

在 Pipeline 中自动执行 SQL Review，包括：

- SQL 语法与兼容性
- SQL 规范
- 高风险 DDL / DML
- 潜在性能风险
- 数据库专项规则

### 基于严重级别的策略

根据问题级别设置不同动作。

例如：

| Severity | Action |
|---|---|
| Info | 记录，不阻断 |
| Warning | 告警，可继续 |
| Critical | 阻断 Pipeline |

### 可配置阈值

企业可以根据自身流程配置：

- 最大 Critical 数量
- 最大 Warning 数量
- 允许忽略的规则
- 必须阻断的规则
- 不同环境的策略

例如测试环境可以相对宽松，而生产发布使用更严格策略。

### Pull Request 反馈

审核结果可以反馈到代码评审流程，使开发者在合并代码之前看到 SQL 问题。

### 流水线报告

生成可用于 CI/CD 的审核结果，例如：

- 通过 / 失败
- 问题数量
- 风险等级
- 规则名称
- SQL 定位
- 修改建议

### API 与 Webhook 集成

SQL Quality Gate 可以通过：

- REST API
- Webhook
- CLI / Script
- DevOps Integration

接入现有流水线。

## 示例

假设提交中包含：

```sql
DELETE FROM orders;
```

PawSQL 识别：

- DELETE 缺少 WHERE 条件
- 可能影响整张表
- 风险级别：Critical

Pipeline 结果：

```text
SQL Quality Gate: FAILED

Critical: 1
Warning: 0

Rule:
DELETE statement without WHERE clause
```

CI/CD 可以因此自动停止后续生产部署。

## 策略即代码

长期来看，SQL Quality Gate 可以作为企业 **SQL Policy as Code** 的执行层。

企业可以把数据库规范从文档转换为可执行策略，例如：

```text
Policy
├─ No DELETE without WHERE
├─ No full table scan on large tables
├─ No forbidden DDL
├─ Index naming convention
├─ Maximum affected rows
└─ Database-specific production rules
```

这样规范不再只存在于 Wiki 或制度文档中，而是直接进入交付流水线。
