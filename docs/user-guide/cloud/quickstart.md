# 三步完成您的 SQL 优化

- 选择/创建工作空间
- 输入待优化 SQL
- 查询优化配置

## 第 1 步：创建工作空间

**工作空间**是进行 **SQL 优化**的上下文环境，一般包含数据表、视图、索引的定义及其上的统计信息。

PawSQL Cloud 支持以下方式创建工作空间：

- 通过数据库连接信息创建工作空间，支持 MySQL / PostgreSQL / openGauss / MariaDB 等数据库
- 通过 DDL 文件创建工作空间
- 通过手工输入 DDL 语句创建工作空间
- 通过数据库 dump 出来的 DDL 创建工作空间

## 第 2 步：输入待优化 SQL

待优化 SQL 是进行查询优化的对象，来源可以是：

- **数据库 SQL 日志**：支持 MySQL 慢日志/通用日志、PostgreSQL 的 SQL 日志、openGauss 的 SQL 日志
- **待优化 SQL 组成的文本文件**：以 `;` 分割
- **手工输入的 SQL**：在文本框中输入，以 `;` 分割

## 第 3 步：创建查询优化

**查询优化**表示在您的**工作空间**内对一组 SQL 查询进行的性能优化诊断，一般包括 SQL 审查、重写优化、索引推荐等。您可以对优化任务的输入、输出、数据源以及执行过程进行配置。

### 基础配置

- **优化 ID**：标识本次优化的 ID。
- **是否仅索引推荐**：控制是否启用重写优化。在 SQL 已经上线、无法立即改写 SQL 的场景下，可以启用此选项，PawSQL 将不会重写 SQL，只基于原 SQL 进行索引推荐。

### 优化验证

- **是否更新 DDL 信息**：是否连接验证数据库以获取最新 DDL 信息。
- **是否启用 What-If 性能验证**：是否对推荐优化建议做性能验证。启用后，优化详情中会提供优化前后 SQL 的执行计划与代价信息，从而确保推荐的优化建议（重写优化与索引推荐）能真实提升数据库性能。
- **性能验证时是否启用 Analyze**：启用后在 What-If 性能验证时获取 SQL 的真实解析与执行时间，避免 MySQL 对中间结果表 explain 的缺陷，代价估算更精确。

> **注意**：后两个性能验证选项应避免在生产库上使用。对于没有内置 what-if（虚拟索引）能力的数据库（MySQL、PostgreSQL 均是如此），性能验证通过「创建推荐索引 → explain 分析执行计划 → 删除推荐索引」的方式完成，在生产库上会消耗一定资源、执行时间可能较长，可能影响生产业务运行。

### 索引推荐配置

- **是否和现有索引去重**：决定推荐索引时是否与现有索引去重。启用此选项适用于不考虑删除现有索引的场景——因为输入的 SQL 并不能代表数据库上的全部 SQL 场景，只考虑新增对输入 SQL 有帮助的索引即可；如果确定输入的 SQL 覆盖了该数据库的所有查询，则可以关闭此选项，用新推荐的索引替换现有索引。
- **是否推荐覆盖索引**：决定推荐索引时是否考虑覆盖索引策略。覆盖索引可以让查询只访问索引而不访问数据表，某些场景下能大幅提升查询性能；但覆盖索引会包含查询条件中没有使用的列，从而增加索引占用的磁盘空间。
- **覆盖索引的最大列数**：推荐覆盖索引时索引的最大列数限制，用于控制覆盖索引占用的空间，在空间受限时仍可利用覆盖索引避免回表。
- **索引的最大列数**：限制索引的最大列数。索引占用磁盘空间，且列数过多会让索引树层级加深、增加索引访问代价。
- **单表最大索引数目**：索引不是免费的，会占用磁盘空间并对 DML 产生负面影响（每写入一行，数据库还必须更新受影响的索引）。PawSQL 通过此项审查单表索引数量并进行告警提示。
