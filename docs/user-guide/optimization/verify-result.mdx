性能验证用于回答两个问题：优化后的 SQL 是否仍然正确，以及它是否在代表性条件下稳定地优于原方案。只比较一次执行耗时或一个预估代价，通常不足以支持生产变更。

## 验证层次

| 层次 | 主要内容 | 适用阶段 |
| --- | --- | --- |
| 静态检查 | 语义、语法、对象和数据库兼容性 | 初步筛选 |
| 计划比较 | 执行计划、算子、估算行数和代价 | 无法直接执行或快速验证 |
| 隔离环境实测 | 耗时、扫描量、CPU、I/O 和结果一致性 | 测试与预发布 |
| 生产观察 | 真实负载下的延迟、吞吐和稳定性 | 已审核上线后 |

## 保证可比性

优化前后应尽量保持：

- 相同数据库类型和版本；
- 相同实例规格和配置；
- 相同数据集和统计信息；
- 相同参数值；
- 相同会话设置和事务隔离级别；
- 相近的缓存和系统负载状态；
- 相同的返回数据消费方式；
- 相同的测量口径。

条件不一致时，应在报告中明确说明，避免把环境差异误判为优化收益。

## 验证流程

<Steps>
  <Step title="定义目标">
    明确希望降低响应时间、扫描量、CPU、I/O、网络数据移动还是资源峰值。
  </Step>
  <Step title="建立基线">
    记录原始 SQL、参数、执行计划、结果校验信息和多次执行指标。
  </Step>
  <Step title="验证正确性">
    比较优化前后的结果集合、数据类型、影响行数或最终数据状态。
  </Step>
  <Step title="运行候选方案">
    在相同条件下多次执行重写 SQL 或创建候选索引后的 SQL。
  </Step>
  <Step title="比较指标">
    同时检查典型值、波动范围和最差情况，不只记录最快一次。
  </Step>
  <Step title="形成结论">
    记录采用、继续调整、拒绝或扩大验证，并附上证据。
  </Step>
</Steps>

## 指标选择

| 指标 | 说明 |
| --- | --- |
| 响应时间 | 用户或调用方实际等待时间 |
| 数据库执行时间 | 数据库端完成 SQL 的时间 |
| 扫描或读取行数 | 反映访问范围是否缩小 |
| CPU 与 I/O | 判断资源成本和系统影响 |
| 排序与临时空间 | 检查是否减少高成本中间操作 |
| 锁等待 | 评估对并发事务的影响 |
| 网络数据移动 | 分布式数据库中的关键成本 |
| 写入延迟 | 新索引对 DML 的额外影响 |

## 参数选择

参数化 SQL 至少应测试：

- 常见业务参数；
- 高选择率参数；
- 低选择率参数；
- 空值或无结果参数；
- 时间范围边界；
- 可能触发不同执行计划的参数。

只使用一个“效果最好”的参数可能掩盖参数敏感性和计划回退。

## 缓存与多次执行

首次执行可能包含编译、磁盘读取或缓存预热成本，后续执行可能受缓存影响。建议：

- 明确冷缓存和热缓存的测试目的；
- 原始与优化方案采用相同顺序策略；
- 执行多次并记录中位数或稳定区间；
- 避免在生产高峰期进行未经批准的压力测试；
- 记录测试期间的系统负载变化。

## 结果正确性

查询 SQL 可以比较：

- 行数；
- 全部结果或抽样结果；
- 关键字段和数据类型；
- 排序和分页结果；
- 聚合值或校验值；
- 双向集合差异。

DML 验证应在隔离环境或可回滚事务中进行，并比较影响行数、目标数据和约束行为。

<Warning>
不要为了验证性能在生产环境反复执行高成本 SQL、创建未经审核的索引或运行大范围数据修改。生产验证必须遵循组织的变更和容量管理要求。
</Warning>

## 如何得出结论

建议采用候选方案时，应同时满足：

- 语义或数据结果验证通过；
- 目标数据库兼容；
- 关键性能指标稳定改善；
- 没有不可接受的写入、锁或资源回退；
- 测试条件具有代表性；
- 已准备审核、发布、观察和回退方案。

## 验证记录

记录 PawSQL 任务编号、工作空间、数据库版本、数据规模、参数、会话设置、原始与候选 SQL、索引状态、执行计划、每次测试指标、结论和负责人。
