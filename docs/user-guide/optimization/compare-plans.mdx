执行计划描述数据库准备如何执行 SQL。PawSQL 可以帮助展示计划结构并对比优化前后的关键差异，但计划需要结合数据库版本、统计信息、参数和实际指标解释。

## 获取计划前检查

- 工作空间对应正确数据库和环境；
- SQL 能够成功解析；
- 数据库连接具备获取计划所需的最低权限；
- 参数值具有代表性；
- 统计信息与当前数据接近；
- 获取计划的方式不会意外执行高风险 SQL。

<Warning>
部分数据库的“实际执行计划”需要真正运行 SQL。对 DML 或高成本查询，应先确认产品行为，并只在安全、隔离且经过授权的环境中使用。
</Warning>

## 阅读顺序

<Steps>
  <Step title="确认计划范围">
    核对 SQL、数据库、参数、计划类型和生成时间。
  </Step>
  <Step title="找到主要访问路径">
    查看表访问方式、使用的索引、扫描范围和过滤条件。
  </Step>
  <Step title="检查连接顺序和算法">
    关注驱动表、连接类型、输入行数和中间结果规模。
  </Step>
  <Step title="检查高成本操作">
    定位排序、聚合、临时结果、回表、重复扫描和分布式数据移动。
  </Step>
  <Step title="比较估算与实际">
    有实际指标时，检查预估行数与实际行数是否存在明显偏差。
  </Step>
  <Step title="比较候选计划">
    确认优化减少了目标成本，并且没有把成本转移到其他关键路径。
  </Step>
</Steps>

## 常见关注点

| 关注点 | 需要判断的问题 |
| --- | --- |
| 全表扫描 | 是合理的小表扫描，还是缺少有效访问路径？ |
| 索引访问 | 索引是否真正过滤数据，是否存在大量回表？ |
| 连接 | 连接顺序和算法是否适合输入规模？ |
| 预估行数 | 与实际行数是否接近，统计信息是否可靠？ |
| 排序与聚合 | 是否产生大量中间数据、临时空间或内存压力？ |
| 重复执行 | 子查询或算子是否被高频重复调用？ |
| 数据移动 | 分布式环境是否发生广播、重分布或跨节点传输？ |
| 并行 | 并行是否带来收益，还是增加协调和资源竞争？ |

## 对比原始与优化计划

建议建立一张对比表：

| 维度 | 原始方案 | 优化方案 | 判断 |
| --- | --- | --- | --- |
| 访问路径 | 记录扫描或索引方式 | 记录新的访问方式 | 扫描范围是否减少 |
| 连接 | 记录顺序和算法 | 记录变化 | 中间结果是否缩小 |
| 预估行数 | 关键节点估算 | 关键节点估算 | 是否更符合实际 |
| 排序与临时数据 | 有无及规模 | 有无及规模 | 是否减少 |
| 总代价 | 数据库提供的估算 | 数据库提供的估算 | 仅作同环境相对比较 |
| 实际指标 | 耗时、行数、资源 | 耗时、行数、资源 | 是否稳定改善 |

## 关于代价

执行计划中的代价通常是数据库优化器用于比较候选方案的内部估算，不等同于毫秒，也不适合跨数据库、跨实例或跨配置直接比较。

代价降低可以作为积极信号，但还应检查：

- 估算行数是否准确；
- 目标 SQL 是否使用相同参数；
- 数据和统计信息是否一致；
- 是否新增了锁、写入或维护成本；
- 实际性能是否支持同一结论。

## 计划发生变化的原因

- SQL 被重写；
- 新建、删除或修改索引；
- 参数值变化；
- 统计信息更新；
- 数据规模或分布变化；
- 数据库版本或配置变化；
- Schema、约束或分区变化；
- 缓存或计划管理机制变化。

## 常见误区

- 认为所有全表扫描都是问题；
- 只看计划第一层或总成本；
- 把预估代价当作实际毫秒；
- 只关注是否使用索引，不看读取行数和回表；
- 忽略参数、统计信息和缓存条件；
- 计划变短就认为一定更快；
- 使用其他环境的计划代表生产环境。
