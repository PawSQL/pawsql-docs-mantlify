## 从“逐条救火”，升级为规模化慢 SQL 治理

生产数据库中的慢 SQL 很少是单点问题。

当业务规模扩大、系统数量增加、数据库实例增多之后，DBA 面对的往往不是：

> “帮我优化这一条 SQL。”

而是：

> “今天生产环境又出现了几百条慢查询，哪些最重要？哪些可以自动优化？哪些需要 DBA 介入？”

传统方式下，DBA 需要不断重复：

```text
查看慢 SQL
    ↓
检查执行计划
    ↓
查看表结构
    ↓
分析索引
    ↓
判断问题原因
    ↓
尝试 SQL 改写
    ↓
设计索引
    ↓
再次验证
```

当慢 SQL 数量从几十条增长到几百、几千条时，单纯依赖人工分析已经很难规模化。

**PawSQL 将慢 SQL 采集、归一化、性能分析、SQL 重写、索引推荐和执行计划验证串联起来，帮助 DBA 建立一套可持续运行的生产 SQL 性能治理流程。**

假设一家金融机构拥有：

```text

```

包括：

```text
MySQL

...
```

每天生产环境产生：

```text
2,000+ 慢查询
```

其中很多 SQL 只是参数不同。

例如：

```sql
SELECT *
FROM orders
WHERE customer_id = 10086
  AND order_status = 'PAID';
```

```sql
SELECT *
FROM orders

  AND order_status = 'PAID';
```

从 SQL 文本来看，它们是三条 SQL。

但从性能治理角度来看，它们实际上属于同一个：

> SQL Pattern

如果 DBA 每条都单独处理，时间会被大量重复工作消耗。

## 慢 SQL 治理真正难在哪里？

生产慢 SQL 治理通常面临四个问题。

### 问题一：慢 SQL 数量太多

假设每天产生：

```text
2,000 条慢 SQL
```

其中：

```text
1,400 条
来自重复 SQL Pattern

400 条
属于已知问题

200 条
需要进一步分析
```

如果没有自动归类能力，DBA 很容易把大量时间耗费在重复 SQL 上。

---

### 问题二：慢不一定代表 SQL 本身有问题

一条 SQL 变慢可能来自：

- SQL 写法问题
- 缺失索引
- 索引失效
- 数据量变化
- 数据倾斜
- 统计信息变化
- 执行计划变化
- 锁等待
- IO 压力
- CPU 资源竞争

因此 DBA 不能只看到：

```text
Execution Time: 12.8s
```

就直接修改 SQL。

首先需要判断：

> 这个问题是否可以通过 SQL 优化解决？

---

### 问题三：知道“慢”，不等于知道“怎么改”

很多监控平台可以告诉 DBA：

```text
这条 SQL 执行了 18 秒
```

但下一步仍然需要人工分析：

```text
为什么慢？

哪里慢？

能否重写？

需要什么索引？

优化后是否真的更好？
```

真正消耗 DBA 时间的是后面的分析过程。

---

### 问题四：优化建议缺少验证

最常见的 SQL 优化建议是：

```text
建议增加索引
```

但真正的问题是：

```text
增加什么索引？

是否已经存在相似索引？

会不会产生冗余索引？

SQL 重写后执行计划是否真的改善？

优化后 Cost 是降低了，还是反而升高了？
```

生产环境需要的是：

> 可验证的优化建议。

而不仅仅是“可能更快”的经验判断。

## 第一步：识别高价值优化对象

慢 SQL 优化不能只按照“单次耗时”排序。

例如：

#### SQL A

```text
单次耗时：30 秒
每天执行：5 次

总耗时：
150 秒
```

#### SQL B

```text
单次耗时：800 ms
每天执行：20,000 次

总耗时：
16,000 秒
```

SQL A 看起来更慢。

但从整体数据库资源消耗来看，SQL B 可能更值得优先优化。

因此慢 SQL 治理需要综合考虑：

- 单次执行耗时
- 执行频率
- 总执行时间
- 扫描行数
- 返回行数
- CPU 消耗
- IO 消耗
- SQL 风险等级

最终建立：

```text
Optimization Priority
```

也就是：

> 优化优先级。

## 第二步：自动分析 SQL 性能问题

假设有一条高频慢 SQL：

```sql
SELECT
    o.order_id,
    o.customer_id,
    o.create_time,
    o.total_amount
FROM orders o
WHERE DATE(o.create_time) = '2026-09-04'
  AND o.customer_id = 10086;
```

PawSQL 可以识别：

```text
性能问题：

过滤字段被函数包裹

DATE(create_time)

潜在影响：

create_time 上的索引可能无法被充分利用
```

这类问题属于典型的：

> Non-SARGable Predicate

即可搜索性较差的查询条件。

---

## 第三步：自动生成 SQL 重写

PawSQL 可以进一步给出等价改写：

```sql
SELECT
    o.order_id,
    o.customer_id,
    o.create_time,
    o.total_amount
FROM orders o
WHERE o.create_time >= '2026-09-04 00:00:00'
  AND o.create_time <  '2026-09-05 00:00:00'
  AND o.customer_id = 10086;
```

原 SQL：

```sql
DATE(create_time) = '2026-09-04'
```

变为：

```sql
create_time >= '2026-09-04 00:00:00'
AND create_time < '2026-09-05 00:00:00'
```

这样可以让数据库优化器更容易使用索引范围扫描。

## 第四步：分析索引

假设当前表有：

```sql
CREATE INDEX idx_orders_create_time
ON orders(create_time);

CREATE INDEX idx_orders_customer
ON orders(customer_id);
```

而 SQL 同时使用：

```text
customer_id = ?
```

以及：

```text
create_time BETWEEN ...
```

PawSQL 可以进一步推荐：

```sql
CREATE INDEX idx_orders_customer_create_time
ON orders(customer_id, create_time);
```

推荐过程不仅考虑：

```text
WHERE 条件
```

还可以结合：

- 等值条件
- 范围条件
- Join 条件
- Order By
- Group By
- 已有索引

进行综合判断。

真正重要的一步，是验证：

## 示例二：相关子查询导致重复扫描

生产环境中另一条 SQL：

```sql
SELECT
    c.customer_id,
    c.customer_name,
    (
        SELECT SUM(o.total_amount)
        FROM orders o
        WHERE o.customer_id = c.customer_id
          AND o.order_status = 'PAID'
    ) AS total_paid
FROM customers c;
```

当 `customers` 表有几十万行时，相关子查询可能重复访问 `orders`。

执行逻辑可能类似：

```text
Customers
   ↓
Customer 1
   ↓
Scan Orders

Customer 2
   ↓
Scan Orders

Customer 3
   ↓
Scan Orders

...
```

PawSQL 可以识别这种查询模式，并评估是否可以解关联。

例如改写为：

```sql
SELECT
    c.customer_id,
    c.customer_name,
    COALESCE(o.total_paid, 0) AS total_paid
FROM customers c
LEFT JOIN (
    SELECT
        customer_id,
        SUM(total_amount) AS total_paid
    FROM orders
    WHERE order_status = 'PAID'
    GROUP BY customer_id
) o
    ON c.customer_id = o.customer_id;
```

执行模式变为：

```text
Orders
   ↓
一次聚合
   ↓
Grouped Result
   ↓
JOIN
   ↓
Customers
```

这类复杂 SQL 重写尤其适合自动化分析。

## 示例三：深分页 SQL

生产环境常见：

```sql
SELECT
    order_id,
    customer_id,
    create_time
FROM orders
ORDER BY create_time DESC
LIMIT 1000000, 20;
```

返回：

```text
20 行
```

但数据库可能需要处理：

```text
1,000,020 行
```

PawSQL 可以识别：

```text
Deep Pagination

OFFSET:
1,000,000

LIMIT:
20
```

并提示使用 Keyset Pagination 等优化方式。

例如：

```sql
SELECT
    order_id,
    customer_id,
    create_time
FROM orders
WHERE create_time < ?
ORDER BY create_time DESC
LIMIT 20;
```

是否能够采用这种改写，需要结合具体业务分页方式判断。

但 PawSQL 可以自动把这类 SQL 从数千条慢查询中筛选出来。

## 示例四：OR 条件导致低效访问

例如：

```sql
SELECT *
FROM orders
WHERE customer_id = 10086
   OR mobile = '13800000000';
```

如果两个字段分别有不同索引，某些数据库或某些数据分布情况下可能无法得到理想访问路径。

PawSQL 可以分析是否存在改写机会，例如：

```sql
SELECT *
FROM orders
WHERE customer_id = 10086

UNION ALL

SELECT *
FROM orders
WHERE mobile = '13800000000'
  AND customer_id <> 10086;
```

具体是否采用该优化，应结合：

- 数据库类型
- 索引
- 数据选择率
- 执行计划

进行验证。

这也是为什么 SQL Rewrite 最好与：

```text
Execution Plan Validation
```

结合使用。

## SQL 归一化为什么重要？

考虑以下 SQL：

```sql
SELECT *
FROM orders
WHERE customer_id = 10001;
```

```sql
SELECT *
FROM orders
WHERE customer_id = 10002;
```

```sql
SELECT *
FROM orders
WHERE customer_id = 10003;
```

归一化后可以统一为：

```sql
SELECT *
FROM orders
WHERE customer_id = ?;
```

于是：

```text
3 条 SQL
```

变成：

```text
1 个 SQL Pattern
```

实际生产环境可能是：

```text
100,000 条执行记录
        ↓
1,000 个 SQL Pattern
```

这样 DBA 才能真正从：

> Query Execution

提升到：

> Query Pattern Governance

即：

> 从单次查询治理，升级为 SQL 模式治理。

## 建立慢 SQL 优先级模型

不是所有慢 SQL 都值得立即处理。

一个完整的慢 SQL 治理平台需要帮助 DBA 判断：

```text
先优化谁？
```

可以考虑：

```text
Priority Score

=
Execution Time

× Frequency

× Resource Impact

× Risk Level
```

例如：

| SQL | 平均耗时 | 执行次数 | 总耗时 | 优先级 |
|---|---:|---:|---:|---|
| A | 25s | 10 | 250s | Medium |
| B | 1.2s | 20,000 | 24,000s | Critical |
| C | 8s | 300 | 2,400s | High |
| D | 400ms | 50,000 | 20,000s | High |

真正有价值的治理，并不是：

> 找出最慢的 SQL。

而是：

> 找出最值得优化的 SQL。

## 多数据库环境下的统一慢 SQL 治理

大型企业通常同时使用：

```text
Oracle
MySQL
PostgreSQL
SQL Server
DB2
openGauss
GaussDB
TDSQL
OceanBase

DM
```

不同数据库：

- SQL 语法不同
- Explain 格式不同
- 索引机制不同
- 优化器策略不同

PawSQL 的价值之一，就是建立统一的：

```text
SQL Analysis
+
SQL Rewrite
+
Index Advisor
+
Plan Analysis
```

能力层。

在上层形成一致的 SQL 性能治理体验。

```text
              SQL 全生命周期

开发阶段
    ↓

阻止高风险 SQL 上线

生产环境
    ↓
Performance Patroller
    ↓

    ↓
PawSQL Optimization
    ↓
持续优化
```

其中：

负责：

> 写 SQL 时发现问题。
