## 从分散的 SQL 工具，升级为统一的 SQL 治理体系

大型企业的 SQL 问题，通常并不是“缺少一个优化工具”。

真正的问题是：

> SQL 分散在不同团队、不同数据库、不同研发阶段和不同管理流程中，却缺少统一治理。

一个大型企业内部可能同时存在：

```text
50+ 业务系统

300+ 开发人员

多个 DBA 团队

数十个数据库实例

多种数据库平台
```

包括：

```text
Oracle
MySQL
PostgreSQL
SQL Server
DB2
openGauss
GaussDB
TDSQL
OceanBase
Kingbase
DM
Hive
...
```

不同团队可能使用完全不同的 SQL 管理方式：

```text
研发团队 A
使用内部 SQL 规范文档

研发团队 B
依赖 DBA 人工审核

研发团队 C
使用自研脚本检查

数据团队
单独维护 Hive SQL 规则

生产运维
通过慢查询日志处理性能问题
```

最终形成的问题是：

> SQL 治理能力存在，但治理体系是碎片化的。

**PawSQL 帮助企业将 SQL 开发、审核、发布、监控、优化和治理指标统一到同一个平台中，建立跨团队、跨数据库、跨研发流程的 SQL Governance 体系。**

---

## 企业 SQL 治理为什么越来越难？

SQL 治理的复杂度通常随着企业规模快速上升。

最常见的四个挑战是：

### 挑战一：数据库越来越多

企业早期可能只有：

```text
Oracle
+
MySQL
```

随着技术演进和信创改造，逐步增加：

```text
PostgreSQL
openGauss
GaussDB
TDSQL
OceanBase
Kingbase
DM
Hive
...
```

不同数据库有不同：

- SQL 方言
- DDL 规则
- 索引机制
- 执行计划
- 优化器行为
- 分布式执行策略

如果每种数据库使用一套独立治理工具，管理复杂度会迅速增加。

---

### 挑战二：SQL 分布在整个软件生命周期

SQL 并不只存在于生产数据库中。

它可能出现在：

```text
IDE
↓
Source Code
↓
MyBatis Mapper
↓
Pull Request
↓
Migration Script
↓
CI/CD Pipeline
↓
Database Release
↓
Production
↓
Slow Query Log
```

如果治理只发生在某一个阶段，例如上线前 DBA 审核，就无法覆盖整个生命周期。

---

### 挑战三：不同团队标准不一致

大型企业经常出现：

```text
Team A
50 条 SQL 规范

Team B
80 条 SQL 规范

Team C
完全依赖 DBA 经验

Team D
没有统一审核
```

即使公司已经有一份：

```text
《数据库开发规范》
```

也很容易停留在：

> 文档标准

而不是：

> 可自动执行的工程标准。

---

### 挑战四：问题发现太晚

传统 SQL 治理经常是：

```text
开发 SQL
    ↓
上线
    ↓
生产出现慢查询
    ↓
DBA 排查
    ↓
紧急优化
```

问题只有在生产环境暴露后，才进入治理流程。

这种方式本质上是：

> Reactive Governance

即：

> 被动治理。

更成熟的企业 SQL Governance 应该尽可能前移：

```text
开发阶段
    ↓
交付阶段
    ↓
生产阶段
```

在每个阶段都建立相应的 SQL 控制点。

## 第一层：开发阶段 SQL Governance

开发人员写 SQL 时，最容易出现的是：

- 非 SARGable 条件
- 低效子查询
- 深分页
- 不合理 Join
- 缺失索引
- 不必要 DISTINCT
- 潜在性能风险

例如：

```sql
SELECT *
FROM orders
WHERE DATE(create_time) = '2026-09-04'
  AND customer_id = 10086;
```

开发环境数据量较小时：

```text
50,000 rows
```

几乎看不出问题。

但生产环境可能有：

```text
80,000,000+ rows
```

Developer SQL Copilot 可以在编码阶段就分析：

```text
DATE(create_time)
```

并给出：

- 问题解释
- SQL 重写
- 索引建议
- 执行计划分析

开发阶段治理的目标是：

> 在 SQL 进入代码仓库之前，把常见问题解决掉。

## 第二层：CI/CD SQL Quality Gate

开发阶段自助优化并不能完全替代组织级控制。

因此企业还需要：

> SQL Quality Gate

即：

> SQL 上线质量门禁。

典型流程：

```text
Developer Commit
        ↓
Pull Request
        ↓
CI/CD Pipeline
        ↓
PawSQL Review
        ↓
SQL Policy Evaluation
        ↓
┌──────────────┬──────────────┐
│ PASS         │ BLOCK        │
│              │              │
│ Merge        │ Fix SQL      │
└──────────────┴──────────────┘
```

检查内容可以包括：

#### 安全风险

- DELETE 无有效条件
- UPDATE 无有效条件
- TRUNCATE
- DROP
- 高风险 DDL

#### SQL 规范

- SELECT *
- 命名规范
- 字段类型规范
- 索引规范
- DDL 规范

#### 性能风险

- 深分页
- 非 SARGable Predicate
- 不合理子查询
- 缺失索引
- 不合理 Join
- 低效聚合

这样 SQL 规范就从：

```text
Database Development Standard.pdf
```

转变为：

```text
Executable SQL Policy
```

即：

> 可执行的 SQL 治理规则。

## 第三层：生产慢 SQL Governance

即使开发和上线阶段已经建立质量门禁，生产系统中仍然会产生新的性能问题。

原因包括：

- 数据增长
- 数据分布变化
- Statistics 变化
- 索引变化
- 新版本发布
- 业务负载变化

因此生产环境仍然需要：

```text
Detect
↓
Analyze
↓
Optimize
↓
Validate
```

PawSQL 可以从慢查询中：

- SQL 归一化
- SQL Pattern 聚类
- 优先级排序
- SQL Rewrite
- Index Advisor
- Execution Plan Analysis
- Optimization Validation

将：

```text
2,000 Slow Queries
```

逐步收敛为：

```text
几十条真正值得 DBA 处理的高价值 SQL Pattern
```

## 一套规则，覆盖多个团队

企业 SQL Governance 最重要的价值之一，是统一标准。

例如企业可以定义：

```text
Enterprise SQL Standard
```

包含：

#### P0 — Critical

```text
DELETE without predicate
UPDATE without predicate
DROP TABLE
TRUNCATE TABLE
```

直接：

```text
BLOCK
```

---

#### P1 — High

例如：

- 高风险 DDL
- 深分页
- 全表扫描风险
- 高成本子查询
- 缺失关键索引

要求：

```text
DBA Review
```

---

#### P2 — Warning

例如：

- SELECT *
- 不合理 DISTINCT
- 可优化谓词
- 非推荐函数写法

允许：

```text
Pass with Warning
```

## 总部统一规则 + 团队扩展规则

大型企业不应该只有一套完全刚性的规则。

更合理的模型是：

```text
Enterprise Baseline Rules
        +
Business Unit Rules
        +
Project-Specific Rules
```

例如：

```text
集团级规则
    ↓
所有项目必须执行

银行核心系统规则
    ↓
增加高风险变更规范

数据平台规则
    ↓
增加 Hive SQL 规范

互联网业务规则
    ↓
增加分页和高并发查询规范
```

这样既可以保证统一底线，也可以满足不同业务特点。

一个企业 SQL Governance 平台必须面对的现实是：

不同数据库可能使用：

```text

Oracle SQL Review Rules

PostgreSQL SQL Review Rules

TDSQL Distributed Rules

Hive Performance Rules
```

但对企业管理者而言，希望看到的是统一治理视图：

```text
One Policy Framework
        ↓
```

PawSQL 的统一分析层可以帮助企业屏蔽底层差异。

## 多数据库不代表“完全相同规则”

统一治理并不意味着：

> 所有数据库执行完全相同的检查。

例如：

#### MySQL

可能关注：

- LIMIT
- 隐式转换
- 索引前导列
- InnoDB 访问路径

#### Oracle

可能关注：

- Hint
- ROWNUM
- Function-Based Index
- PL/SQL

#### PostgreSQL / openGauss

可能关注：

- Seq Scan
- Join Strategy
- CTE
- Distribution

#### Hive

可能关注：

- Partition Pruning
- Data Skew
- MapJoin
- Global Sort

因此正确的统一治理应该是：

```text
Unified Governance Framework
            +
Database-Specific Intelligence
```

## 从 SQL 规范文档升级为 Policy as Code

很多企业已经有几十页甚至上百页：

```text
《SQL开发规范》
```

问题是：

> 文档本身不会阻止错误 SQL 上线。

真正成熟的方式是将规范转变为：

> Policy as Code

例如：

```text
Rule:
UPDATE without WHERE

Severity:
Critical

Action:
Block Pipeline
```

或者：

```text
Rule:
Deep Pagination

Threshold:
OFFSET > 100000

Severity:
High

Action:
Require Review
```

SQL 治理因此从：

```text
人记住规范
```

转变为：

```text
系统自动执行规范
```

## 自定义企业 SQL 规则

每个大型企业都会有自己的数据库规范。

例如：

```text
索引名称必须以 IDX_ 开头

禁止字段使用某些数据类型

单事务 DML 不得超过指定行数

备份表必须符合命名规则

夜间批量 SQL 可以使用不同阈值
```

统一治理平台需要允许企业将这些规范配置为：

```text
Custom SQL Rules
```

并在：

```text
Development
CI/CD
Release Review
```

多个环节重复使用。

这可以避免：

```text
同一条规范
由不同工具重复实现
```
