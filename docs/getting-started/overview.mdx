PawSQL 是一个面向开发人员、测试人员、数据库管理员以及企业数据库治理团队的 **SQL 工程与治理平台**，帮助团队在 SQL 的整个生命周期中持续发现问题、优化性能并控制上线风险。

从开发人员在 IDE 中编写第一条 SQL，到 CI/CD 流程中的上线检查，再到生产环境中的慢 SQL 治理和企业级 SQL 治理，PawSQL 将 **SQL 规范审核、重写优化、索引推荐、性能验证与执行计划分析**整合到统一的平台中。

> **让 SQL 质量与性能成为软件工程流程的一部分。**

---

## 什么是 PawSQL

SQL 性能问题通常并不是在生产环境中突然出现的。

低效的 SQL 写法、不合理的索引、潜在的全表扫描、数据库迁移后的执行计划变化，以及缺乏统一的 SQL 开发规范，都可能在开发阶段被引入，并最终演变为生产环境中的性能或稳定性问题。

PawSQL 的目标，是将 SQL 治理从传统的 **“生产问题发生后再优化”**，转变为贯穿软件开发生命周期的 **持续 SQL 工程化治理**。

```text
开发人员
   │
   ▼
编写 SQL
   │
   ▼
SQL 审核与优化
   │
   ├── 规范审核
   ├── 重写优化
   ├── 索引推荐
   ├── 执行计划分析
   └── 性能验证
   │
   ▼
CI/CD 质量门禁
   │
   ▼
生产环境
   │
   ▼
慢 SQL 治理
```

通过 PawSQL，SQL 优化不再只是数据库管理员的事后工作，而可以成为研发流程的一部分。

## 覆盖 SQL 全生命周期的平台

PawSQL 可以覆盖 SQL 从开发到生产的多个关键阶段。

| 阶段 | 典型问题 | PawSQL 能力 |
|---|---|---|
| **开发阶段** | SQL 编写质量依赖个人经验 | 在 IDE 中进行 SQL 检查与优化 |
| **代码评审** | 人工评审难以完整发现 SQL 问题 | 自动执行规范审核与优化分析 |
| **CI/CD** | 高风险 SQL 可能进入生产环境 | 建立 SQL 上线质量门禁 |
| **数据库迁移** | 数据库差异可能导致兼容性和性能变化 | 对迁移 SQL 进行统一扫描与治理 |
| **生产环境** | 慢 SQL 数量大，依赖人工逐条分析 | 批量分析和治理慢 SQL |
| **企业治理** | 不同团队、数据库和规则体系难以统一 | 建立统一的企业 SQL 治理平台 |

## 核心能力

PawSQL 不仅帮助团队发现 SQL 问题，还进一步帮助开发人员和数据库管理员理解问题，并给出可执行的优化方案。

### 规范审核

在 SQL 进入生产环境之前，根据 SQL 开发规范和数据库最佳实践自动识别潜在风险。

典型检查包括：

- SQL 编写规范
- DDL 和 DML 风险
- 查询性能风险
- 索引使用问题
- 数据库最佳实践
- 企业自定义 SQL 规则

→ [了解规范审核](/reference/audit-rules/index)

---

### 重写优化

PawSQL 优化引擎可以基于 SQL 语义和数据库优化原理，对查询进行自动化重写。

例如：

```sql
SELECT *
FROM orders
WHERE customer_id = 1001
   OR customer_id = 1002;
```

可以识别为：

```sql
SELECT *
FROM orders
WHERE customer_id IN (1001, 1002);
```

对于更复杂的查询，PawSQL 还可以分析子查询、关联、聚合、谓词下推等优化机会，在保持 SQL 语义一致的前提下生成候选优化方案。

→ [了解重写优化](/reference/optimizer-rules/index)

---

### 索引推荐

索引推荐不仅需要判断哪些字段出现在查询条件中，还需要综合考虑：

- 过滤条件
- 关联条件
- 排序与分组
- 已有索引
- 字段选择率
- 联合索引设计
- 数据库优化器行为

PawSQL 对 SQL 与数据库结构进行联合分析，并生成针对查询负载的候选索引方案。

→ [了解索引推荐](/features/index)

---

### 性能验证

一个逻辑上合理的优化建议，并不意味着在真实数据库中一定更快。

因此，PawSQL 可以进一步结合数据库优化器，对优化前后的 SQL 进行性能验证，例如比较：

- 优化器代价
- 访问路径
- 关联方式
- 预估行数
- 索引使用情况
- 执行计划

帮助团队从：

**“这个 SQL 理论上应该更快”**

进一步走向：

**“数据库优化器也确认这个方案更优。”**

→ [了解性能验证](/features/index)

---

### 执行计划可视化

复杂执行计划通常包含大量节点，阅读和分析成本较高。

例如：

```text
嵌套循环
 ├─ 索引扫描
 └─ 哈希关联
     ├─ 顺序扫描
     └─ 位图堆扫描
```

PawSQL 执行计划可视化工具可以将传统文本执行计划转换为更容易理解的可视化执行树，帮助开发人员和数据库管理员快速识别：

- 全表扫描
- 高代价算子
- 关联策略
- 索引使用情况
- 基数估算
- 代价分布

→ [了解执行计划可视化](/features/index)

## 融入现有研发流程

SQL 不只存在于数据库客户端中。

它可能存在于：

- IDE
- 代码仓库
- CI/CD 流水线
- SQL 审核平台
- 数据库迁移项目
- 慢查询日志
- 应用性能监控系统
- 企业内部研发平台

因此，PawSQL 提供多种集成方式，使 SQL 分析和治理能力能够进入现有研发流程。

```text
                     ┌─────────────────┐
                     │     PawSQL      │
                     │   SQL 分析引擎   │
                     └────────┬────────┘
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
          ▼                   ▼                   ▼
      开发人员             CI/CD              数据库管理员
          │                   │                   │
      IDE 优化          SQL 质量门禁          慢 SQL 分析
          │                   │                   │
          └───────────────────┼───────────────────┘
                              │
                              ▼
                         SQL 统一治理
```

根据使用场景，可以通过 IDE 插件、API、Webhook、MCP 或 PawSQL Server 将 PawSQL 集成到研发和数据库管理流程中。

## 面向多数据库环境设计

现实中的企业数据库环境通常并不只有一种数据库。

一个组织可能同时运行多种关系型数据库、分布式数据库、国产数据库以及数据仓库。

不同数据库拥有不同的 SQL 方言、优化器、索引机制和执行计划。

PawSQL 从设计之初就面向 **多数据库 SQL 治理**，通过统一的分析入口处理不同数据库中的 SQL，同时保留针对不同数据库的优化逻辑。

→ [查看支持的数据库](/getting-started/supported-databases)

## 从 SQL 优化走向 SQL 工程化治理

传统 SQL 优化通常发生在生产问题出现之后：

```text
性能问题
   ↓
发现慢 SQL
   ↓
人工分析
   ↓
手工优化
```

PawSQL 希望建立另一种工作方式：

```text
编写 SQL
   ↓
规范审核
   ↓
优化
   ↓
验证
   ↓
质量门禁
   ↓
上线
   ↓
持续治理
```

SQL 因此不再只是应用中的一段字符串，而成为软件工程过程中可以被 **分析、验证、治理和持续改进的工程资产**。

PawSQL 关注的核心，是让 SQL 质量和性能真正进入软件研发生命周期。
