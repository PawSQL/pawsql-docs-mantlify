# 金融生产环境实战：PawSQL 驱动 TDSQL-MySQL 慢查询优化

某大型金融客户把 PawSQL 的智能巡检与优化能力引入 TDSQL-MySQL 生产环境，对 400 多条慢查询做系统性优化，覆盖 11 个业务系统，持续近两个月。最终召回率 76.6%，超七成慢查询自动完成优化，人工只需处理剩余少数深水区案例。

## 召回率 71.4% → 76.6%

400 多条慢 SQL 中，269 条存在可优化空间。PawSQL 首个版本独立完成有效优化的比率（召回率）是 71.4%（192 条）；补充规则覆盖后，最新版本提升到 76.6%（206 条）。

![召回率对比](/images/blog/tdsql-recall-comparison.png)

超过七成的慢查询由 PawSQL 自动输出方案并验证，资深 DBA 不必再逐条手工调优，可以把精力投向架构设计和数据治理。

## 中位数性能提升 671.4%

PawSQL 对 227 条慢 SQL 完成性能验证。

![性能提升分布](/images/blog/tdsql-performance-distribution.png)

- 中位数性能提升 671.4%，一半以上的优化建议带来 7 倍以上增益
- 30% 的案例提升超百倍，全表扫描改为索引扫描，IO 成本显著下降
- 仅 17% 的案例提升低于 10%，对应大结果集查询：索引减少了扫描行数，但数据传输成本不变

## 归因：索引与重写双引擎

针对 192 条有效优化案例，PawSQL 做了归因分析，拆出性能提升的来源。

![归因分析](/images/blog/tdsql-attribution.png)

### 索引优化：贡献近半

智能索引推荐是主力。192 条有效优化里，纯索引推荐 90 条，占 46.9%。它不止判断「缺什么索引」，还能识别索引的多种加速效应：

- 加速查找：为过滤条件、连接列创建精准索引，全表扫描改为索引扫描
- 避免排序：利用索引有序性，消除 `ORDER BY`、`DISTINCT`、`GROUP BY` 引发的文件排序
- 复合索引避免回表：设计覆盖查询所需全部列的复合索引，省去二次回表

### 索引 + 重写组合：占 46.4%

89 条有效优化（46.4%）来自「索引推荐 + 查询重写」的组合方案。查询重写很少单独出现，通常需要配合索引调整；PawSQL 的引擎能识别这种依赖关系，协同推荐。

![重写算法命中](/images/blog/tdsql-rewrite-algorithm-hits.png)

重写改变了 SQL 结构后，索引推荐引擎会基于新结构重新计算最优索引，保证推荐结果始终匹配当前查询形态。

## 剩余 23.4% 未覆盖

76.6% 的召回率意味着 63 条可优化 SQL 未被独立覆盖。

![未覆盖原因](/images/blog/tdsql-uncovered-reasons.png)

未覆盖的 63 条里，三分之一属于深度 SQL 改写：PawSQL 的重写引擎已覆盖 40 多种算法，但派生表物化、LATERAL JOIN 改写、多表关联顺序深度调整等场景仍待扩展。

SQL 优化分浅层和深层。浅层（缺索引、明显语法问题）已高度自动化；深层（执行计划结构级调整）是下一阶段方向。从 71.4% 到 76.6% 的提升说明，规则体系的迭代速度决定召回率的上限。

### 不同业务场景的差异

11 个业务系统的效果差异，反映出 SQL 模式与召回率之间的关联：

![业务场景召回率](/images/blog/tdsql-scenario-recall.png)

- 内部管理系统：召回率 84%–87%。SQL 模式规整，以单表索引缺失和多表关联优化为主，索引推荐和基础重写规则覆盖充分
- 财务分析和客户分析系统：当前 35%–43%，优化后 50%–71%。大量使用派生表和窗口函数，结构复杂
- 核心业务系统：111 条慢 SQL，召回率 70%。未覆盖案例集中在 IN 子查询改写和大结果集翻页优化

## 从逐条人工诊断到七成自动完成

266 条慢 SQL 经 DBA 人工复核。在「可优化但当前无效」的案例中，DBA 人工补充的深度改写方案（LATERAL JOIN 改写、STRAIGHT_JOIN 纠正、函数索引替代）约占三分之一。SQL 审核平台的价值在于把人从大量浅层问题里解放出来，聚焦需要深度判断的少数案例。

后续将派生表物化、LATERAL JOIN 改写、复杂 EXISTS 解关联纳入自动化后，召回率预计再提升 8–10 个百分点。
