Optimization history preserves the SQL, analysis context, recommendations, and decisions associated with a task. Use it to revisit evidence, compare versions, and prepare review or governance records.

## Find a task

Depending on the release, filters may include task name or ID, creator, date, project, workspace, database engine, status, SQL text or fingerprint, and recommendation type.

If a task is missing, first verify the project, time range, workspace, filters, and permissions.

## Reconstruct original context

Before reusing a conclusion, inspect:

- task time and PawSQL version;
- database engine and version;
- workspace and metadata timestamp;
- SQL, parameters, and schema;
- findings, rewrites, indexes, and plans;
- partial failures;
- recorded acceptance or validation status.

<Note>
Historical tasks retain the context used when they were created. Refreshing the current workspace does not automatically reanalyze an old task.
</Note>

## Re-run when

- SQL changed;
- the database version changed;
- schema, constraints, or indexes changed;
- data scale or distribution changed materially;
- parameter behavior changed;
- the PawSQL engine or rule version changed;
- fresh plan or performance evidence is required.

Link the new task to the previous one in your review record.

## Export checklist

- [ ] Correct task and time range selected.
- [ ] Single-task versus filtered-set scope confirmed.
- [ ] SQL, object names, and plan data classified and sanitized.
- [ ] Format suits the recipient.
- [ ] The exporter is authorized to share the data.
- [ ] Database, workspace, and analysis time are included.

<Warning>
An optimization report may contain complete business SQL, schema names, execution plans, and scale information. Do not distribute production reports through public links.
</Warning>

## What to include with a shared result

- Optimization objective;
- database and environment;
- primary recommendation;
- validation conditions and evidence;
- acceptance decision;
- risk and rollback plan;
- owner and next action.

Do not send a rewritten statement or index DDL without the original problem and supporting evidence.

## Retention by use case

| Use case | Evidence to retain |
| --- | --- |
| Code review | Original and candidate SQL, rule, correctness test |
| Index change | Rationale, plan comparison, capacity, write impact |
| Production governance | Baseline, measurements, deployment, observation |
| Audit trail | Task ID, people, decision, approval, versions |

## Troubleshooting

| Symptom | Check first |
| --- | --- |
| Historical task missing | Project, date, workspace, permissions, retention policy |
| Current advice differs | SQL, versions, parameters, metadata, plan date |
| Export incomplete | Partial task, role permission, selected scope, format capability |
