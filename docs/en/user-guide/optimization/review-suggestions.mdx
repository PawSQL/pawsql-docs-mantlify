An optimization task may contain several result types. Read them together: a rewrite changes the query shape, an index changes available access paths, and the plan or validation result explains whether the candidate is likely to help.

## Recommended order

<Steps>
  <Step title="Verify context">Check engine, version, schema, workspace, and input SQL.</Step>
  <Step title="Check completeness">Confirm parsing and object resolution; identify skipped or partially failed work.</Step>
  <Step title="Address risk">Review blocking and high-severity findings first.</Step>
  <Step title="Evaluate rewrites">Compare semantics and read applicability conditions.</Step>
  <Step title="Evaluate indexes">Compare candidates with the complete existing-index inventory.</Step>
  <Step title="Inspect evidence">Use plans, estimates, or measurements to support the decision.</Step>
</Steps>

## Result types

| Result | Question answered | How to use it |
| --- | --- | --- |
| Review finding | Does the SQL violate a policy or introduce risk? | Determine remediation or exception handling |
| SQL rewrite | Is there a semantically equivalent alternative? | Compare behavior, complexity, and plan |
| Index recommendation | Can a better access path improve this workload? | Assess overlap, benefit, and maintenance cost |
| Execution plan | How does the database intend to run the SQL? | Locate scans, joins, sorts, and data movement |
| Validation | Is there measurable evidence of improvement? | Support acceptance or rejection |

## Review rewrites

Check output columns and types, duplicate semantics, `NULL` behavior, joins, filters, aggregation, ordering, pagination, and modification scope. Shorter SQL is not automatically better SQL.

## Review indexes

Check table and schema, key order, included columns, filter predicates, existing-index overlap, write overhead, storage, and the breadth of the workload that benefits.

## Prioritize work

| Priority | Typical examples |
| --- | --- |
| High | Data-safety risk, unbounded modification, critical high-frequency slow SQL |
| Medium | Stability issue, repeated large scans, rewrite or index with verifiable benefit |
| Low | Maintainability guidance, low-frequency query, uncertain benefit |

## Record the decision

For each candidate, store status, owner, rationale, test conditions, plan or performance evidence, intended release, and rollback method.

<Warning>
Severity, optimizer cost, and estimated benefit inform a decision; they do not authorize an automatic production change.
</Warning>
