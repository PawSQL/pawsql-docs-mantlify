## Stop Bad SQL Before It Reaches Production

Modern development teams automate code testing, security scanning, builds, and deployments through CI/CD pipelines.

SQL, however, is often still reviewed manually.

A developer submits a database change, a DBA reviews the SQL, comments on potential risks, waits for revisions, and reviews it again.

As development teams scale, this process quickly becomes a bottleneck.

**PawSQL brings automated SQL review and performance analysis into your CI/CD pipeline, allowing teams to detect risky and inefficient SQL before it reaches production.**

---

## The Challenge

Imagine a development organization with:

- 300+ developers
- 50+ applications
- MySQL, PostgreSQL, Oracle, SQL Server, and distributed databases
- dozens of releases every week
- hundreds or thousands of SQL changes every month

A typical database release process may look like this:

```text
Developer
    ↓
Commit SQL
    ↓
Pull Request
    ↓
DBA Manual Review
    ↓
Developer Modification
    ↓
DBA Re-review
    ↓
Release
```

This model works when the development team is small.

At scale, several problems emerge.

### DBA Becomes a Delivery Bottleneck

DBAs must manually inspect large numbers of SQL statements, including:

- DDL changes
- DML scripts
- application queries
- data migration scripts
- schema modifications

Routine SQL reviews consume significant DBA capacity that could otherwise be spent on architecture, capacity planning, and production performance engineering.

---

### SQL Review Standards Are Difficult to Enforce Consistently

Different DBAs may apply different standards.

Different teams may also maintain their own database development guidelines.

For example:

```text
Team A
50 SQL rules

Team B
80 SQL rules

Team C
Manual DBA review

Team D
No SQL review
```

As a result, SQL quality increasingly depends on individual experience rather than a consistent engineering process.

---

### Performance Problems Are Often Found Too Late

Traditional SQL audit tools mainly check coding conventions.

They may detect:

```sql
SELECT *
FROM orders;
```

or:

```sql
UPDATE orders
SET status = 'CLOSED';
```

But many production SQL problems are syntactically correct and still inefficient.

For example:

```sql
SELECT *
FROM orders
WHERE DATE(create_time) = '2026-09-04'
  AND customer_id = 10086;
```

The SQL is valid.

But applying a function to `create_time` may prevent the database from efficiently using an index on that column.

These issues may not become visible until the table contains millions of rows.

## What PawSQL Checks

PawSQL combines **SQL governance** and **SQL performance optimization** in the same analysis process.

### SQL Coding and Safety Rules

PawSQL can identify potentially risky SQL patterns such as:

- `SELECT *`
- `UPDATE` without appropriate predicates
- `DELETE` without appropriate predicates
- dangerous DDL operations
- excessive transaction sizes
- problematic data type usage
- improper index definitions
- naming convention violations

Example:

```sql
DELETE FROM orders;
```

PawSQL can classify this statement as a high-risk operation and prevent it from passing the SQL Quality Gate.

---

### SQL Performance Risks

PawSQL also analyzes SQL patterns that may cause poor execution performance.

Examples include:

- non-SARGable predicates
- unnecessary `DISTINCT`
- inefficient correlated subqueries
- redundant joins
- inefficient `OR` conditions
- deep pagination
- improper aggregation
- unnecessary sorting
- missing indexes

For example:

```sql
SELECT *
FROM orders
WHERE DATE(create_time) = '2026-09-04'
  AND customer_id = 10086;
```

PawSQL may identify:

```text
Performance Issue

Function applied to indexed column:

DATE(create_time)

Potential impact:

The database may not efficiently use an index on create_time.
```

PawSQL can then suggest an equivalent rewrite:

```sql
SELECT *
FROM orders
WHERE create_time >= '2026-09-04 00:00:00'
  AND create_time <  '2026-09-05 00:00:00'
  AND customer_id = 10086;
```

## Example: Detecting an Inefficient Query Before Release

Consider an API used to retrieve customer orders.

A developer submits:

```sql
SELECT order_id,
       customer_id,
       create_time,
       status
FROM orders
WHERE DATE(create_time) = '2026-09-04'
  AND customer_id = 10086
ORDER BY create_time DESC;
```

Assume the table contains:

```text
orders
--------------------------------
Rows:            80,000,000
customer_id:     indexed
create_time:     indexed
```

The query passes functional testing because the development environment contains only a small dataset.

PawSQL analyzes the SQL during the pull request.

---

### Step 1 — Detect the Performance Risk

PawSQL identifies:

```text
Rule

Function on indexed column

Expression

DATE(create_time)

Risk

The expression may prevent the optimizer from
using the create_time index efficiently.
```

---

### Step 2 — Generate an Equivalent Rewrite

PawSQL can recommend rewriting the predicate as a range condition:

```sql
SELECT order_id,
       customer_id,
       create_time,
       status
FROM orders
WHERE create_time >= '2026-09-04 00:00:00'
  AND create_time <  '2026-09-05 00:00:00'
  AND customer_id = 10086
ORDER BY create_time DESC;
```

---

### Step 3 — Recommend an Index

Based on query predicates and ordering requirements, PawSQL may recommend an index such as:

```sql
CREATE INDEX idx_orders_customer_create_time
ON orders(customer_id, create_time);
```

Instead of providing a generic recommendation such as:

> Add an index.

PawSQL analyzes query structure and predicate relationships to generate a more actionable recommendation.

---

### Step 4 — Validate the Optimization

Where database connectivity and execution-plan analysis are available, PawSQL can compare the execution strategy before and after optimization.

For example:

```text
Before Optimization

Table Scan / Large Range Scan
Estimated Cost: 18452


After Optimization

Index Range Scan
Estimated Cost: 327
```

The optimization recommendation can therefore be evaluated before it is merged into the release branch.

## Define Your SQL Quality Gate

Different organizations have different database governance policies.

A financial institution may treat certain SQL operations as critical:

```text
TRUNCATE TABLE
DROP TABLE
UPDATE without selective predicate
DELETE without selective predicate
```

A SaaS company may focus more heavily on performance:

```text
Full table scan risk
Deep pagination
Missing indexes
Correlated subqueries
Large joins
```

PawSQL allows SQL rules to become part of the engineering process rather than remaining only in internal database development documents.

A typical policy might look like:

| Severity | CI/CD Behavior |
|---|---|
| Info | Record only |
| Warning | Allow merge with warning |
| Error | Require developer confirmation |
| Critical | Block pipeline |

This creates a measurable and repeatable SQL governance process.
